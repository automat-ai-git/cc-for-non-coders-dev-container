# Продвинутое демо: штаб реагирования на инцидент

## Сценарий

После релиза часть клиентов не может выгружать отчёты, а у нескольких enterprise-клиентов повреждены последние сохранённые фильтры. Информация меняется по ходу расследования. Команда должна одновременно восстановить сервис, оценить затронутых клиентов и подготовить коммуникацию без неподтверждённых обещаний.

## Подготовка

Agent Teams экспериментальны и по умолчанию выключены:

```bash
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude
```

В `.claude/agents/` лежат три роли. Teammates создают разные файлы, поэтому не конфликтуют при записи.

## Основной промпт

```text
Создай agent team для реагирования на инцидент.

Состав:
1. teammate service-analyst — используй одноимённый agent type. Разбери incident-log.md и affected-customers.csv, оцени масштаб, версии причин и неизвестные. Пиши только analysis/impact-assessment.md.
2. teammate incident-commander — используй одноимённый agent type. Собери план восстановления, контрольные точки и критерии отката. Пиши только outputs/recovery-plan.md.
3. teammate customer-comms — используй одноимённый agent type. Подготовь статус-апдейт и отдельный шаблон письма enterprise-клиентам. Пиши только outputs/customer-update.md.

Требования к координации:
- service-analyst отправляет подтверждённый масштаб двум другим teammates;
- customer-comms не публикует ETA, пока incident-commander его не подтвердит;
- incident-commander обязан запросить у service-analyst список неизвестных перед финальным планом;
- при расхождении данных агенты обсуждают его, а не выбирают удобную версию;
- исходные файлы не менять.

После завершения teammates сам подготовь outputs/executive-brief.md: факты, влияние, что сделано, неизвестные, решения руководителя и время следующего обновления.
```

## Что должно произойти

- Аналитик замечает, что первые записи журнала говорят о 18 клиентах, а поздняя проверка — о 27.
- Коммуникационный агент убирает фразу «данные не потеряны»: журнал подтверждает повреждение сохранённых фильтров у четырёх клиентов.
- Командир отделяет workaround от полного исправления и задаёт критерии отката.
- Teammates обмениваются сообщениями по существу, а не только отчитываются lead.

## Проверка результата

1. В публичном сообщении нет названий клиентов и внутренних гипотез.
2. В enterprise-письме есть конкретный workaround, канал эскалации и время следующего обновления.
3. ETA помечен как подтверждённый или отсутствует.
4. `executive-brief.md` различает факт, гипотезу и неизвестное.
5. Ни один teammate не редактировал чужой файл.

## Усложнение во время работы

Когда команда уже начала, добавьте в `incident-log.md` новую строку: workaround увеличивает нагрузку на API. Затем скажите lead:

```text
Появились новые данные в incident-log.md. Разошли обновление команде, пересмотрите план и клиентское сообщение. Не переписывайте историю — добавьте changelog.
```
